# API mock 계약

기준은 `shared/api/apiTypes.ts`의 생성된 OpenAPI 타입이다. 화면에 맞춰 별도의 응답 구조를 만들지 않는다.

API가 없다고 판단하기 전에는 dev Swagger 원문(`https://dev-api.azitcrew.com/v3/api-docs`)과 비교한다. 생성 타입은 마지막 갱신 시점의 스냅샷이다. `pnpm --filter web generate:api-types`는 기본적으로 이 dev Swagger에서 재생성하며, 다른 계약 원문은 `API_SWAGGER_URL`로 지정할 수 있다. 로컬 설정은 `.env.local`과 `.env`를 읽는다.

- 핸들러는 `mockApi.get/post/put/patch/delete`로 작성한다. OpenAPI에 정의된 전체 경로(`/api/v1/.../{crewId}`)를 전달하면 MSW 파라미터 경로로 변환된다.
- 경로와 메서드로 요청 JSON, 경로 파라미터, 성공 응답 타입이 결정된다. resolver는 응답 객체를 반환하고 공통 코드가 JSON으로 직렬화한다.
- 데이터 파일의 각 응답에는 `satisfies MockResponse<'get', '/api/v1/...'>`를 붙인다. 성공 응답은 code/message와 result를 채운다. Void API만 result를 생략한다.
- 핸들러 목록은 `MockHandler[]`로 검사한다. 원시 `http.get()` 등으로 만든 핸들러는 등록할 수 없다.
- 실패 시 `MockApiError(code, message, status)`를 던진다. 예상하지 못한 예외를 성공 응답으로 바꾸지 않는다.
- 생성된 API 타입은 직접 수정하지 않는다. 스키마를 갱신한 뒤 타입 검사가 가리키는 mock을 함께 수정한다.

`pnpm --filter web typecheck`는 앱의 참조 프로젝트까지 검사한다. `contracts.typecheck.ts`에는 실제로 발생했던 잘못된 응답과 경로/메서드 조합이 포함돼 있으며, 이를 허용하게 되면 검사가 실패한다.

`pnpm --filter web test`는 실제 MSW 요청을 통해 설정, 출석, 일정 달력, 크루, 장소, 인증 응답을 확인한다. 테스트에서는 처리하지 않은 요청을 오류로 간주한다.

## 동작 범위

현재 localhost 개발 모드와 `dev.azitcrew.com`에서 기존 설정대로 MSW가 활성화된다. 외부 지도/OAuth 서비스와 실제 백엔드의 동작을 이 테스트로 검증하지는 않는다.

약관·프로필 수정, 크루 생성·가입 신청·취소, 일정 생성·수정·삭제·참여·취소는 메모리에 반영되며 새로고침하면 초기화된다.

일정 원본은 `state/schedules.ts` 한 곳에서 관리한다. 크루별 목록·달력·상세·참여자 명단과 홈의 내 일정·다음 일정 안내는 이 상태에서 파생한다. 목록은 문서의 날짜 우선순위(`date > startDate/endDate > yearMonth > 현재 월`)와 런 종류를 적용한다. 생성자는 자동 참여하며, 참여 인원은 명단에서 계산한다.

초기 데이터는 오늘 기준 +1일(크루 1 정기런, 본인 생성), +5일(크루 1 번개런, 미참여), +2일(크루 2 번개런, 미참여)이다. ID는 각각 1·2·3이고 이후 생성은 4부터 증가한다. 크루 1에서는 리더, 크루 2에서는 일반 멤버다. 테스트에서는 `resetScheduleMocks()`로 상태와 ID를 초기화한다.

일정 권한·입력 검증과 문서의 중복 참여·정원·60분 간격 조건을 처리한다. 수정/삭제는 출석 가능 시간 시작(모임 1시간 전)부터 제한하고, 참여/취소는 모임 1시간 후 마감한다. GPS·네이티브 출석과 실제 서버의 모든 출석 상태 전이는 이번 웹 QA 범위에 포함하지 않는다.

크루 정보·멤버·가입 요청·초대 코드는 `state/crews.ts`의 상태를 공유한다. 생성·가입 신청·신청 취소·수정·재발급·승인·거절·방출·탈퇴·해산 후 재조회에도 변경을 반영한다. 생성자는 리더로 가입하고 고유한 6자리 초대 코드를 받는다. 리더 권한과 본인 방출·리더 탈퇴 제한을 검사하며, 탈퇴·해산한 크루는 가입 크루 및 홈의 내 일정에서 제외한다. `resetMemberMocks()`는 이 크루 상태도 초기화한다.

미가입 크루 `한낮러너스`(ID 3)의 초대 코드는 `NOON03`이다. 가입 신청은 REQUESTED, 취소는 CANCELLED 상태로 바뀐다. OpenAPI 문서의 취소 후 1시간·탈퇴 후 24시간 재신청 제한과 중복 가입 제한을 적용한다. 가입/신청 중인 크루 수는 기존 화면 정책과 같은 최대 3개이며 거절 이력은 이 수에 포함하지 않는다. 실제 서버의 크루 수 제한 정책은 별도로 검증하지 않았다.

다른 계정인 리더의 결정을 QA할 때는 `resolveMockJoinRequest(3, true | false)`로 승인/거절을 모의한다. 승인 시 멤버 수와 가입 크루도 갱신된다. 이는 QA helper이며 API의 리더 권한 검사를 우회하는 엔드포인트는 추가하지 않는다. 마이페이지는 대기 요청이 있을 때 10초마다 내 크루를 갱신하고, 재진입/창 포커스 시에도 재조회한다. 새로고침하면 초기 fixture로 돌아가므로 상태 전이는 같은 세션에서 확인한다.

회원 프로필·선택 약관·로그인 계정 상태는 `state/member.ts`에서 관리한다. 프로필 수정 후 크루 멤버와 일정 생성자·참여자의 현재 회원 정보도 같은 원본에서 파생한다. 닉네임은 화면과 mock이 `entities/User/model/profile.ts`의 검증을 공유한다. 이미지는 현재 URL 또는 기본 이미지 URL을 허용하며 네이티브 커스텀 이미지 업로드는 이번 QA에 포함하지 않는다.

선택 약관은 부분 갱신하고 변경 일시를 문서의 `yyyy-MM-dd HH:mm:ss` 형식으로 반환한다. 두 필드 모두 null/생략인 요청은 `INVALID_INPUT_VALUE`로 거절한다. 계정 연동 해제는 목록에 반영하고 마지막 로그인 수단을 보호한다. 복수 계정 상황은 `setMockProvidersForQa()`로 준비할 수 있지만 실제 외부 OAuth를 대체하지 않는다.

서비스 탈퇴는 리더 소속 크루가 있으면 `CANNOT_SERVICE_WITHDRAW_AS_LEADER`로 거절한다. 모의 탈퇴 성공 시 인증 상태를 로그아웃으로 바꾸며, 실제 계정 삭제·30일 복구 유예·소셜 연동 해제 배치는 구현하지 않는다.

크루별 알림은 최신 계약의 `GET /api/v1/members/me/crews/notifications`와 `PATCH /api/v1/members/me/crews/{crewId}/notifications`를 사용한다. 기존 화면 전용 샘플 목록은 제거했다. mock 알림 설정은 `state/crews.ts`의 가입 크루 상태에 연결돼 실제 크루 이름·이미지와 JOINED 상태를 반영한다. 최초 설정은 정기런·번개런 모두 true이고, 전체 토글은 두 값을 함께 변경한다. 개별 토글이 하나라도 꺼지면 allEnabled는 false다. 부분 갱신에서 allEnabled를 먼저 적용하고 개별 값으로 덮어쓰며, 세 항목이 모두 null/생략이면 400을 반환한다. 탈퇴 시 설정을 지우고 재가입 승인 후 모두 켜짐으로 초기화한다.

선택 약관의 notificationAgreed=true는 가입 중인 모든 크루의 알림을 켠다. false는 크루별 설정을 보존한다. 크루별 토글 변경은 선택 약관 동의 값을 바꾸지 않는다. 로컬에서는 이 두 API도 MSW가 응답하며, 뒤로 갔다 재진입하면 값을 유지하지만 새로고침하면 초기 fixture로 돌아간다. 실제 백엔드 저장·푸시 발송은 이 mock QA로 검증하지 않는다.

## 알림함·공지사항의 API 연결 대기 범위

2026-11-15에 dev Swagger 원문(57개 경로)을 다시 확인했다. 크루별 알림 설정 API는 있지만 알림함 목록·읽음 처리·공지사항 목록·상세 API는 정의돼 있지 않다. 따라서 해당 화면에 임의의 HTTP 경로나 API DTO를 만들지 않는다.

현재 이 화면들은 `entities/Notification/api/previewRepository.ts`의 메모리 미리보기 저장소를 사용한다. `model/types.ts`는 화면 모델이며 백엔드 계약이 아니다. 기존 샘플 공지 내용은 유지하고, 일정 알림의 대상 ID는 초기 mock 일정 1·2·3 및 크루 1·2에 맞췄다. 실제 이벤트에서 알림을 생성하거나 푸시를 발송하지 않는다.

읽음 상태는 상세 이동 전에 저장하며 뒤로 가기·재진입에는 유지하고 새로고침하면 초기화한다. 크루 관련 이동은 계약이 있는 내 크루 조회 API로 현재 가입 상태와 리더 권한을 확인한다. 이동 정보 누락·권한 상실·읽음 저장 실패는 안내 후 알림함에 머무르며 읽음 상태를 바꾸지 않는다. 공지 목록은 마이페이지에서 열 수 있고, 없는 공지 ID는 빈 화면 대신 돌아가기 안내를 표시한다.

`configureNotificationPreviewForQa()`로 목록·공지 누락, 지연, 조회·읽음 실패를 주입하고 `resetNotificationPreview()`로 초기화할 수 있다. 이 QA는 화면의 재시도·중복 클릭 방지·상세 이동을 검증하며 실제 백엔드 저장이나 알림 수신을 검증하지 않는다. 계약이 추가되면 생성 타입을 갱신하고 이 저장소를 실제 요청으로 교체해야 한다.

## 기타 범위

출석 로그·달력·통계는 `state/attendances.ts`에서 같은 월·크루 조건으로 파생한다. 초기 데이터는 2026년 11월의 크루 1 기록 3개(출석 2·결석 1), 크루 2 기록 1개(출석 1)다. 실제 출석·포인트 적립은 구현하지 않는다.

전체 백엔드를 대체하지 않는다. 다른 계정의 실제 승인, 방출된 본인의 재가입, 실제 알림 수신, 네이티브 공유는 별도 검증 대상이다. 추가 시나리오에는 상태 변경과 재조회 테스트를 함께 추가한다.

## 배송지

배송지 목록·등록·수정·삭제는 `state/addresses.ts`의 상태를 공유한다. 최신 dev Swagger의 정렬 규칙(기본 배송지 우선, 나머지는 최신 등록순), 첫 배송지 자동 기본 설정, 새 기본 배송지 설정 시 기존 기본 해제, 기본 배송지 삭제 금지를 적용한다. 생성·수정·삭제 성공 응답은 Void 계약대로 식별자나 result를 추가하지 않는다.

화면과 mock은 필수 텍스트·isDefault 및 OpenAPI의 연락처 pattern(`^\d{2,3}-\d{3,4}-\d{4}$`)을 `entities/Address/model/validation.ts`에서 함께 검증한다. 연락처 표시는 02 및 3자리 국번을 지원한다. 계약에 없는 우편번호 길이·수령인 글자 수 제한은 추가하지 않는다.

초기 배송지는 ID 1·2이고 ID 1이 기본 배송지다. ID 900은 소유권 오류 QA용 다른 회원의 주소로, 내 목록에 표시하지 않는다. `resetAddressMocks()`로 초기화하고 `setMockAddressesForQa([])`로 첫 등록·빈 목록을 준비할 수 있다. 새로고침하면 초기 fixture로 돌아가며 실제 백엔드 저장을 검증하지 않는다.

주소 검색은 실제 카카오 우편번호 SDK를 사용한다. 도로명/지번 선택을 구분하고, 입력 화면별 키로 검색 결과를 전달한다. 수령인·연락처는 유지하며 다른 주소를 선택하면 이전 상세주소는 비운다. SDK 로드 실패는 재시도를 제공한다. `submitMode: false`로 검색의 iframe 방문기록이 앱의 뒤로 가기와 URL 동기화를 방해하지 않도록 한다([공식 안내](https://postcode.map.kakao.com/guide#attributes)).

목록의 선택 강조와 저장된 기본 배송지 표시는 구분한다. 배송지 변경 완료 전에는 기존 기본 배송지의 삭제 제한을 유지한다. 저장·삭제 중에는 스피너와 disabled 처리를 적용하고, 실패 시 입력값·선택·삭제 확인 창을 보존해 재시도할 수 있다.

## 공통 인증·경로 QA

회원 상태는 생성된 `SocialLoginResponse.status`의 ACTIVE·PENDING_TERMS·WITHDRAWN·DELETED를 사용한다. 이전 화면에서 가정했던 PENDING_ONBOARDING 등 크루 상태는 회원 인증 상태에 추가하지 않는다. 회원 상태와 크루 가입·방출 상태는 구분한다.

`state/auth.ts`는 기존 개발용 `__mock_auth_status__` 값을 읽는다. 값이 없으면 기존 개발 환경대로 ACTIVE이고, LOGGED_OUT은 재발급에 401을 반환한다. PENDING_TERMS·WITHDRAWN·DELETED도 QA할 수 있다. 개발 도구의 Mock 로그인 버튼은 외부 OAuth 없이 상태를 전환하며, 이 키는 실제 서비스 인증 수단이 아니다.

가입 약관 `POST /api/v1/members/terms`도 계약에 맞는 Void 응답으로 처리한다. 네 가지 필수 동의 중 하나라도 true가 아니면 REQUIRED_TERMS_NOT_AGREED를 반환한다. 성공 시 ACTIVE 및 선택 동의 상태를 저장한다. 화면은 성공 후 토큰을 갱신하고 크루 생성·가입으로 이동한다. 약관 저장은 성공하고 토큰 갱신만 실패한 경우에는 약관을 재전송하지 않고 갱신만 재시도한다.

인증 접근 판단은 `app/routes/authPolicy.ts`와 `AuthInitializer`에서 처리하고, 보호 화면은 `withAuth`에서 인증 확인 전/상실 시 내용을 렌더링하지 않는다. 공개 약관과 404는 로그인 여부·인증 서버 일시 오류와 관계없이 읽을 수 있다. 일반 로그인 콜백은 인가 코드 교환을 처리하며, 계정 연동 콜백은 현재 회원 인증을 요구한다. ACTIVE의 추가 크루 온보딩 직접 진입도 유지한다.

초기화와 동시 401의 재발급은 `shared/auth/model/session.ts`에서 공유한다. 인증 재요청과 Ky의 네트워크 재시도 횟수는 별도로 구분한다. 재발급 5xx/네트워크 오류는 기존 세션을 보존하고, 인증 거절 또는 갱신 토큰의 재요청도 401이면 세션을 종료한다. 로그아웃/회원 상태 상실 때 회원 캐시를 지우며 늦은 재발급 응답으로 이전 세션을 되살리지 않는다.

회원 상태 403을 크루 방출로 해석하지 않는다. 기존 방출 주소는 실제 내 크루 목록에 EXPELLED가 있을 때만 안내하고, 없으면 마이페이지로 돌아간다. 최신 계약에 없는 `/members/me/confirm-status` 호출은 제거했다. 공통 뒤로 가기는 이전 화면이 없는 직접 진입에서 홈으로 교체하고, 이전 화면이 있으면 기존 경로로 복귀한다.

33개 등록 웹 경로를 ACTIVE로 점검했고, 29개 보호 경로의 LOGGED_OUT·PENDING_TERMS 직접 진입에서 회원 데이터 요청 없이 각각 로그인·가입 약관 화면으로 이동하는 것을 확인했다. 계정 연동의 외부 OAuth, 실제 HttpOnly 쿠키 회전·만료, 실제 백엔드 접근 제어, 앱 전용 기능은 이 MSW QA의 검증 범위가 아니다. ACTIVE 회원의 `needsTermsUpdate=true` 재동의 흐름은 가입 완료 전용 API와 구분해 별도 계약·기대 동작 확인이 필요하다.
